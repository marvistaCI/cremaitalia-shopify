# Crema Italia — SKU Standard

**Source of truth:** this file (`docs/standards/sku-standard.md`) in the theme repo.

> **This is a normative repo document, NOT a fourth Standard.** The three Standards — Brand, Store
> Operating, Collaboration — are versioned, rendered to stamped PDFs, delivered to OneDrive and
> certified by the render-trust badge. This document is none of those things, deliberately. It
> carries **no version number**, has no render, and is cited **by section title**. It lives here
> rather than in the Cowork tree because ownership follows enforcement: a SKU is generated by code
> from records held in Shopify, so the normative text belongs where the generator lives, under
> version control. Documents in other lanes point at these section titles; they never restate the
> rules, because restating is what drifts.
>
> Do not "fix" this by giving it a version and a PDF. A format that changes is a format that has
> already failed — see *Governance*.

## What a SKU is, and what it is not

A Crema Italia SKU is a **ten-character label**, not a key.

Shopify does not parse SKUs. The field is plain text on the **variant**, never decomposed, never
used to resolve a relationship, and **not required to be unique** — Shopify accepts duplicates
silently and gives each variant its own independent inventory pool, which is a defect waiting to
happen rather than a feature (`production_build_spec.md` §16.2). Coffee links to roaster, and
roaster to region, through **metaobject references** (`production_build_spec.md` §13.4).

**No system may key on a SKU or on any segment of one.**

So the SKU encodes facts that already live somewhere else, which is the two-homes problem this
project keeps removing. It earns its place for the one thing a metafield cannot do:

> **It travels.** The roaster, the freight forwarder, the customs broker, the 3PL, a packing slip,
> a scanner and the printed bag label all see the SKU. None of them can see a metafield.

**A SKU is GENERATED from the records it describes and never typed by hand.** A generated SKU
cannot disagree with them. Hand-entry reintroduces exactly the disagreement the format exists to
avoid.

## The format

**`TRRRPPPPSS`** — ten characters, each `A-Z0-9`.

| Segment | Len | Meaning |
|---|---|---|
| `T` | 1 | Type class |
| `RRR` | 3 | Source — who supplied it |
| `PPPP` | 4 | Product, scoped within `RRR` |
| `SS` | 2 | Size |

```
C002000125   coffee, roaster 002, their product 0001, 250 g
C00200011K   the same coffee, 1 kg
S0010001EA   a collection, curated by Crema Italia
I0070001EA   a printed card, from the card printer
K0080001EA   a presentation box, from the box printer
B0090001EA   a Bottega item, from its manufacturer
```

**The identifier is always ten characters. The Shopify SKU *field* may carry the identifier plus
one documented suffix** — see *The Offerta pick suffix*, which is the only one that will ever
exist. A parser must read ten characters plus an optional suffix, never a fixed width.

## The type class

| `T` | Class | Lot controlled? | Notes |
|---|---|---|---|
| `C` | Coffee | **Yes** | The only lot-controlled, freshness-governed class |
| `B` | Bottega | No | Non-perishable retail goods |
| `S` | Collection | No — its components are | A BOM SKU; see Store Operating Standards §7 |
| `I` | Info card | No | Printed matter held as stock |
| `K` | Package | No | Presentation boxes held as stock |

**One sentence governs every downstream rule:**

> **Lot control, roast-date capture and the freshness windows apply to class `C` only.**

That is what a 3PL, a WMS configuration and a receiving procedure need in order to know which items
require date capture at goods-in. It is also why a collection cannot be class `C`: a collection is
not itself lot-controlled, its components are.

## The source segment

**`RRR` identifies the SOURCE — who supplied the item — and means the same thing for every class.**
It resolves to an entry in the vendor register (see *Where SKUs are assigned*), which is also the
purchasing list, so every SKU names the party a purchase order is raised against.

- Class `C` — the roaster
- Class `B` — the manufacturer or supplier
- Class `S` — Crema Italia, which curates collections
- Class `I` — the card printer
- Class `K` — the box printer

**An alternative was considered and rejected.** `RRR` could have carried the *owner* for classes
`S`, `I` and `K` — a shared code across a collection and its card and box, so that the siblings
differ by one character and a scanner can verify the set. It was rejected because the pick list
already names every BOM line explicitly (Store Operating Standards §7 transmits the BOM **per
order**), so the substitution shortcut solves a problem that is already solved, while its cost is
real: the card printer and box printer would disappear from the SKU entirely, and `RRR` would mean
two different things depending on class.

**The consequence, stated so nobody assumes otherwise:** a collection, its card and its box share
no visible pattern. **That relationship lives in the BOM and only in the BOM.** It cannot be
reconstructed from the SKUs, and no warehouse procedure may assume it can.

**The Bottega independence rule.** A Bottega item carries the code of whoever supplied it, and it
belongs to no roaster even when a partner roaster's brand appears on it. A roaster-branded cup is a
Bottega product, not that roaster's product: it must not appear on the roaster's page, must not
answer a roaster filter, and must not join any roaster-scoped report. This is already enforced in
the theme by a taxonomy predicate rather than by testing for a roaster field
(`production_build_spec.md` §12). **Bottega stands alone.**

## The product segment

**`PPPP` is scoped per source.** Each roaster numbers their own coffees; `RRR` plus `PPPP` together
identify a product uniquely. Global numbering was considered and rejected: it offers no advantage,
since nothing may key on `PPPP` alone, and it would require a central registry to hand out codes.

Allocation runs `0001`–`9999`, then `A000`–`A999`, `B000`–…. Capacity is not a constraint.

**`0000` is reserved and is never allocated.** Any SKU containing it is a generation defect, which
makes it a cheap validation rule.

**Nothing may key on `PPPP` alone.** It is meaningless without its `RRR`.

## The size segment

| `SS` | Size |
|---|---|
| `10` | 100 g |
| `25` | 250 g |
| `50` | 500 g |
| `1K` | 1 kg |
| `EA` | each — Bottega, collections, cards, boxes |

Size is what makes the SKU **variant-level**, which matches Shopify's grain: Shopify carries the
SKU on the variant. The four coffee sizes are the Roaster Guide's standard sizes.

**`EA` cannot distinguish variants, so for class `B` one SKU is one sellable variant, not one
product.** A moka pot in three cup sizes, or a machine in three colours, is three SKUs with three
`PPPP` values — not one `PPPP` with three sizes. Getting this wrong produces several variants
carrying an identical SKU, which Shopify accepts in silence while splitting their stock into
separate pools.

**A coffee SKU exists for every size the roaster will label, which is not the same as every size we
list.** 100 g is sold only inside collections (Store Operating Standards §1), so `…10` is a real
SKU that is never a standalone purchasable product. Because SKUs are handed to the roaster for
label printing, and a label plate costs money, the assignment record should mark which sizes are
actually to be produced.

## There is no shelf segment

Type, source, product and size do not change over a bag's life. **Shelf does** — a lot ages out of
Roccia, Sorpresa or Selezione into Offerta.

A SKU that encoded shelf would therefore require **physically re-labelling every bag** when its
stock changed shelves. It does not, so the printed label stays true for the life of the bag.

**Do not "improve" this by adding a shelf character.** A proposal to do exactly that was made and
withdrawn for this reason.

What declares the shelf to the storefront is a **product tag**, and each shelf page is a Shopify
automated collection keyed on that tag (`production_build_spec.md` §13.9). Not `product.type`,
which carries the taxonomy, and deliberately not the SKU.

## The Offerta pick suffix

Two prices require two Shopify products: one variant cannot hold both the fresh and the marked-down
price, and collections contain products rather than variants. So when aged units are sold alongside
fresh stock of the same coffee, the Offerta listing is a separate short-lived product referencing
the same coffee record, and **FIFO becomes per shelf** — the fresh listing ships the oldest fresh
lot, Offerta ships the oldest aged lot.

**The suffix is a pick instruction, not a second SKU.**

- The Offerta product's SKU is the base ten characters plus **`-OFF`**.
- Permitted on **class `C` only**, and it is **the only suffix that will ever exist**.
- **It is never printed on a bag, a carton or a label.** Physical goods carry the ten-character
  code and nothing else. The suffix exists in Shopify and on the pick line.
- **It is not what puts the product on the Offerta shelf.** The tag does that. The two mechanisms
  serve different audiences and must not be conflated: the tag is read by the site, the suffix by
  the warehouse.
- **The pick meaning:** the base SKU means pick oldest first from stock inside the freshness
  window; the base plus `-OFF` means pick oldest first from stock past that window and inside the
  Offerta band. Both boundaries are named settings, never typed numbers (Store Operating Standards
  §5.5), and both are evaluated **at the moment of pick**.

**Preferred physical handling — one bin, two pick conditions.** The stock is not moved and not
stickered; the suffix on the pick line selects which age band the picker draws from within the same
location, evaluated against the lot's roast date. This preserves the printed label perfectly and
costs no physical touch.

**Whether it is achievable is a 3PL qualifying question, not an assumption.** Some warehouse
systems can express an age-band allocation rule within one location and some require physical
segregation. If a candidate requires a bin transfer, that falls back to a suffixed SKU with a
**marked bin** — never to per-bag stickering — **and the per-unit transfer cost must be quoted
before selection.**

**What Shopify will and will not do here, because it is easy to over-trust.** Because the two
listings are separate products they are separate variants, therefore separate inventory records,
and Shopify holds their counts apart at a single location with no location work at all. But it
**holds** those numbers; it does not derive, maintain or police them. It has no lot or batch
tracking, so the split is an assertion a person makes once and nothing re-checks. It will never
notice that the two pools are the same physical good in the same bin, and it will never detect a
pick taken from the wrong age band. **A periodic reconciliation of the 3PL's on-hand report against
the two Shopify pools is the control that catches the drift**, and it is worth doing whichever
physical handling a 3PL turns out to support.

## Collections, cards and boxes

A collection's card and box are **stocked, picked, non-lot-controlled inventory** held at the 3PL,
each with its own SKU sourced from whoever printed or made it. Their cost is what gives Store
Operating Standards §2.3's `packaging_cost` a derivation rather than a typed figure.

The card is **one hybrid card per collection** — the roaster stories plus the taste and preparation
notes for each coffee in that collection, designed for that collection.

**Cards must carry no lot-specific content.** A card printed with a roast date cannot be held as
stock.

**An aged collection is its own collection, not a suffixed one.** `-OFF` is class `C` only. A
collection holds no inventory and is assembled on order, so it cannot itself age; what ages is its
components, and Store Operating Standards §7 auto-pauses a collection when a component leaves its
window. Selling aged stock as a collection therefore means **deliberately curating a new
collection**, with its own `PPPP`, priced on the aged factor in Store Operating Standards §2.2, and
its availability gate reads the Offerta band rather than the fresh window.

## Where SKUs are assigned

**In production**, SKUs are generated from the roaster, coffee and product records held in Shopify
(`production_build_spec.md` §13.4, §13.9), never typed.

**Until then**, the register of assigned SKUs is
`Operations\In USA\shopify\Master Data\CremaItaliaSKUMasterBuilder.xlsx` in OneDrive. It is a
living register rather than a document: **it carries no version in its filename**, and it is the
authority for which codes have been handed out.

Two of its properties are load-bearing and must survive any rebuild of it:

- **Source codes and product sequences are assigned once and then frozen.** A formula may *propose*
  the next free value; the assigned value is then held as a literal. A code derived from row
  position renumbers every entry below an insertion or a sort, silently re-pointing SKUs that may
  already be printed on a bag.
- **It emits only what goes on a bag.** No `-OFF`, no shelf, no lot. That is what makes it directly
  usable as the label-printing handoff to a roaster.

**CI is not where hand-entry is caught, and should not be expected to be.** A lint over this
repository can catch a SKU literal written into theme code or documentation outside this standard's
own examples, and a malformed or shelf-encoded one. It cannot see a SKU typed into a Shopify
variant field. The guard against hand-entry is the generator, plus validation at product onboarding
(`production_build_spec.md` §15.2).

## Governance

> **The type-class enumeration is extensible. The structure is frozen.**
>
> New type classes may be added at any time. **Segment order, segment lengths and total length are
> frozen at the first production SKU assignment**, and can change afterwards only by re-labelling
> every bag in existence.

No second suffix. No shelf segment. No keying on a segment. No hand-typed SKU.

## Where this standard is consumed

| Consumer | What they see |
|---|---|
| Roaster | The ten-character code on the retail label and master carton, supplied by us with the label template |
| Packing list / commercial invoice | One line per SKU per bag size, carrying lot and roast date |
| 3PL — receiving | The ten-character code; class `C` requires roast-date capture |
| 3PL — picking | The ten-character code, plus `-OFF` where the age band differs |
| Shopify | The full string on the variant; never parsed, never keyed on |
| Storefront | Never displayed to a customer as an identifier |
